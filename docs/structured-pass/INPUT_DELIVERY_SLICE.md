## Implementation boundary and acceptance

Reuse the existing guidance, document, reference-media and analogue mechanisms.
Add only the bounded declared-input route/configuration changes shown necessary
by the checkpoint. No project-root write/read expansion, new provider settings,
permission workaround, general file browser or new reference-acquisition system.

Offline acceptance must show:

- Both role configurations and role bridges can retrieve every declared item,
  with the pinned content and page identities. Distinguish text, images and PDFs;
  do not credit content that one adapter cannot deliver.
- Missing, changed, stale and undeclared inputs fail before being credited as
  delivered. Changing a manifest/path cannot admit an arbitrary host file or
  project source; existing source and ownership boundaries remain intact.
- Fresh sessions and restored review reads use the same pinned evidence. Current
  task instructions remain separate from historical receipt text.
- The corrected notes work through the existing document lifecycle; no root
  writer is added. Root paths remain refused by ordinary document registration.
- A small advisory in the existing project process check flags a root
  `WORKING_NOTES.md`, including when a canonical copy also exists. Absence or a
  canonical-only file stays quiet; the advisory does not change the gate's exit
  status. A deliberate removal of the check must fail its test. Existing corpus
  cleanup is outside this slice.

Test the complete manifests and assembled inputs offline, including negative
controls. This does not prove receipt by a running client: provider-backed
delivery, both updated tool declarations and the reviewer's hook-disabled check
remain part of separately authorized launcher admission. Pin no new live profile
and launch no semantic pass here.
