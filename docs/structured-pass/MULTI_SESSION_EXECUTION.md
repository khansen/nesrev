# Sequential session admission

The [multi-session scope](MULTI_SESSION_SCOPE.md) uses one frozen investigation
plan, followed by the existing editing and independent-review pair. This page
describes the integrated launcher. Native acceptance of the complete recipe is
still pending; a passing capacity calculation does not authorize inference.

Preparation creates a separate immutable Codex profile for each investigator
and one for the editor, all sharing one isolated Codex login home. The reviewer
uses its existing isolated Claude home. Every profile names the same pair root.
The ordered investigator list binds each entry ID, profile and admission report
to the workflow plan. The pair pins these files along with the ordinary editor
admission report. A profile for another entry, source, login home or model cannot
join the plan.

Investigator admission measures its actual assignment, startup, source and RAM
responses, final instructions, opening message and native declaration. The
[measured-format policy](MULTI_SESSION_RATE_POLICY.md) applies to every session.
Checkpoint output, phase-contract growth and assignment delivery retain their
charged caps. A declared predecessor handoff adds that predecessor's full cap
to the consumer's price. Independent partitions receive the checked transition
receipt without loading earlier semantic handoffs. The assignment lists any
handoffs that a continuation must read. No handoff in prose substitutes for the
service's citation and coverage checks.

One grant pins the launch configuration and gives the shared wall deadline,
per-invocation time, invocation count, Claude response limit and application
permission. The plan allows each investigator once, then at most five ordinary
turns: implementer, reviewer, implementer, reviewer, implementer. A three-turn
approval path can finish early. Additional owner-steered turns or extensions
cannot silently enlarge this fixed plan.

The implementer worker runs the investigators sequentially through the existing
heavy-run wrapper and process supervisor. The reviewer watcher waits for the
ordinary publication notification. After every investigator, the coordinator
reconciles its finished native transcript with the service journal and publishes
the checked immutable checkpoint. Before editing, it verifies the union of all
required coverage and the final native audits again. Later edit/review turns
keep the same editor context and retain the investigation as historical evidence
after publication; this build does not renew facts into a fresh editing context.

Each client invocation consumes a persisted slot before it starts. Both native
adapters require that slot's message, profile, phase, grant and deadline, then
claim it exactly once. Concurrent claims, erased client history, a changed
editor thread, an extended adapter budget or an expired grant refuse. A fresh
profile therefore cannot reset the shared allowance. Claude's distinct response
IDs continue to accumulate in its existing shared budget; Codex reports native
token usage without imposing a new token cap.

Recovery can reconcile a coordinator interruption only when the supervisor
record proves a zero exit and completed cleanup, the adapter has exactly one
finished investigation run, and its final native audit validates the staged or
already accepted checkpoint. It does not spawn a replacement client. A partial
checkpoint stays partial. An interrupted client, uncertain usage, missing
cleanup evidence or late compaction refuses recovery. Normal pair closeout and
application checks remain necessary before the approved candidate is applied.

The next acceptance step is the reserved eight-invocation offline recipe:
three investigation contexts, including a partial continuation, followed by
the existing five-turn review/rework/closeout path. It must exercise the actual
tmux launcher, watcher, shared budgets, final declarations, write checks and
application. Until that succeeds, this is implementation evidence, not complete
native admission.
