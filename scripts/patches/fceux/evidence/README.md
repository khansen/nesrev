# Reviewable FCEUX evidence

This packet accompanies the optional local workaround. Every referenced artifact
is tracked or generated by the commands below from public upstream source.
Review does not require the author's installed runtime, project corpus, home
directory, temporary files or conversation history. Executables are not shipped.

Verify the packet from this directory with `shasum -a 256 -c SHA256SUMS`.
The synthetic fixture and exact Lua script used by the captures are included in
the [upstream attachment bundle](../upstream/startup-race-attachments.zip), with
their own checksums. No commercial ROM or personal configuration is required.

These are captured observations, not machine-independent guarantees. All five
captures completed through the supervisor and then reported emulator exit `-11`
during intentional shutdown. The packet does not establish normal-speed/audio
quality or gameplay identity. Sampled startup-race evidence for the newer,
different upstream base is in the [separate issue handoff](../upstream/STARTUP_ISSUE.md).

<a id="redactions"></a>
## Redactions and evidence limits

The logs are retained outputs with local path prefixes replaced by labels:
`<work>` is the build/validation workspace, `<fixtures>` is the extracted
synthetic fixture bundle, `<nesrev>` is the checkout and `<installation>` is
the optional runtime installation. Revision checks use `<mutation>` and
`<temporary-directory>` for disposable test locations. These are labels, not paths to
existing resources. A cold-start result's trace/log is stored beside that result
in this packet, regardless of its recorded workspace label.
Trailing whitespace in build logs is removed.

No result, duration, error, frame, compiler diagnostic or exit code was changed.
[original-output-hashes.json](original-output-hashes.json) records the hashes
before path normalization for provenance; checking those originals is not a
review prerequisite. This is not a signed build attestation. Source hashes and
build commands allow a reviewer to rebuild independently, but differences in
toolchains and generated metadata can change the executable hash.

Earlier harness setup mistakes are not counted as emulator or regression-test
failures: a corpus probe initially assumed one ROM per directory, and a reduced
config-control fixture initially omitted transitive headers. The config-control
log here is from the subsequent successful compile and actual failing test.
The first tmux experiment exposed a trailing-semicolon argument bug; the final
adapter and the portable test below cover it. No successful rerun is used to
relabel those earlier attempts.

Review of `68b882339` found that the original activation kept paths through
`current`, so switching the symlink changed subsequent captures' executable.
The revised profile checks and exports one physical release. The old profile
records above remain historical; `profile-revision.json` records the new checks.
The supervisor already resolves the executable per capture, but that did not
pin selection across captures and it does not record an executable hash.

## Repeat checks from a clone

From the NESrev root:

```sh
python3 scripts/patches/fceux/test_profile.py
python3 scripts/patches/fceux/test_profile.py --tmux
make check-agent-playbooks check-repo-hygiene
git diff --check
```

The first command uses synthetic installation files and skips the tmux case.
The second creates its own server on an explicit socket, checks a bare-launch
negative control, forwarding into initial/split/respawned panes and new windows,
semicolon handling and missing-variable refusals, then stops that server. It
does not connect to user sessions or start an emulator/agent.
`make test` runs the non-tmux profile cases;
the private-server test remains opt-in. A machine without tmux skips that case.

For a negative control, copy the three profile/test files into a disposable
directory and run the copied test there. Replacing the checksum command with
`true` must fail the damaged-installation test. Replacing the adapter with a
plain `exec tmux "$@"` must fail environment forwarding. Removing its trailing-
semicolon escaping must fail the same real-server test. Never mutate the
reviewed checkout or an installed profile.
Restoring the original activation must fail the symlink-switch regression;
removing the config-directory check or either required checksum entry check
must fail the corresponding refusal test.

Apply the [config patch](../2.7.0-no-config.patch) to a fresh checkout of its
recorded base and run the standalone CTest commands in the
[upstream handoff](../upstream/README.md#resume-contribution). Restore only the
base `configSys.cpp` in a disposable copy to reproduce the failing control.
The [local build recipe](../LOCAL_BUILD.md#rebuild-local) covers the combined
emulator. The public source/patches supply the inputs; local bundles are unused.

## Optional bounded capture reproduction

Live emulator runs require a built candidate and permission to run desktop code.
They are not needed to execute the profile or config tests. Use a fresh workspace
you choose and extract the upstream attachment bundle into it. Set
`FCEUX_REVIEW_WORK` to that workspace and `FCEUX_CANDIDATE` to the candidate
executable. For each attempt, use a new copy name and output directory:

```sh
mkdir -p "$FCEUX_REVIEW_WORK/cold-1/config"
cp "$FCEUX_CANDIDATE" "$FCEUX_REVIEW_WORK/cold-1/fceux"
FCEUX_CONFIG_DIR="$FCEUX_REVIEW_WORK/cold-1/config" \
QT_QPA_PLATFORM=minimal SDL_VIDEODRIVER=dummy \
python3 scripts/run_fceux_trace.py \
  --fceux "$FCEUX_REVIEW_WORK/cold-1/fceux" \
  --rom "$FCEUX_REVIEW_WORK/startup-race-attachments/own-test.nes" \
  --lua "$FCEUX_REVIEW_WORK/startup-race-attachments/maximum-supervised.lua" \
  --output-dir "$FCEUX_REVIEW_WORK/cold-1" \
  --max-frames 60 --timeout 8 --completion-line COMPLETE
```

Check each result and trace for exactly `FRAME 1` through `FRAME 60`, then
`COMPLETE`, preserving every timeout or failure. Record binary, ROM, Lua and
supervisor hashes and distinguish supervisor status from emulator exit. For
config-preservation checks, seed an isolated config first and compare its bytes
afterward. Never infer first-launch reliability from repeated launches alone.
